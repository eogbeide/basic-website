Primary spine: Google Cloud SRE practitioners and the class SRE implements DevOps / Engineering for Reliability series. Learn reliability as an engineering discipline: define SLIs/SLOs, use error budgets, reduce toil, instrument metrics/logs/traces, build actionable alerts, operate incidents and turn failures into measurable system improvements.

Benchmark: Google Cloud publishes the SRE Fundamentals, class SRE implements DevOps, Engineering for Reliability, OpenTelemetry/Cloud Trace and Prometheus learning videos publicly. Build-Along Checkpoints

  • Checkpoint 1: Choose a real service and map user journeys to candidate SLIs; define at least two SLOs, measurement windows, an SLA boundary where relevant and an explicit error-budget policy.
  • Checkpoint 2: Instrument the service with application metrics plus structured logs and OpenTelemetry traces; include request success, latency and dependency signals with correlation across boundaries.
  • Checkpoint 3: Build dashboards around user-centered reliability and golden signals; create an SLO/error-budget view and remove or downgrade at least one noisy infrastructure-only alert.
  • Checkpoint 4: Add Prometheus-style instrumentation and actionable alerting with runbook links, ownership and escalation; test alert delivery and prove each page requires a human action.
  • Checkpoint 5: Inventory recurring operational toil, automate one manual task and quantify time/risk reduction; define capacity headroom and one safe progressive-change or rollback mechanism.
  • Checkpoint 6: Run a controlled incident game day with clear roles and communications, capture detection/mitigation/recovery timestamps, then write a blameless postmortem with owned preventive actions.

7-Day Independent Capstone

  • Day 1: Define service journey, SLIs/SLOs, error budget, failure taxonomy, escalation threshold and reliability-versus-velocity policy.
  • Day 2: Instrument metrics, structured logs and OpenTelemetry traces; verify cross-service correlation and build a reliability dashboard.
  • Day 3: Add Prometheus metrics, SLO-burn alerts and runbooks; tune pages to be user-impact-oriented, actionable and owned.
  • Day 4: Automate one measured toil source; add capacity/headroom tracking plus a safe deployment rollback or feature-control path.
  • Day 5: Inject latency, dependency and partial failures; measure MTTD/MTTR and refine telemetry, alerts and runbooks from evidence.
  • Day 6: Run a timed incident with command, operations and communications roles; restore service and validate escalation/handoffs.
  • Day 7: Publish repo/config, SLO policy, dashboards, alert rules, automation proof, incident timeline, postmortem and action backlog.

SRE - Measure, Alert, Respond & Learn

Build a reliability operating system for a real service. Completion requires user-centered SLOs and error budgets, correlated telemetry, high-signal alerts, measured toil reduction, incident command, recovery evidence and a blameless postmortem whose action items measurably improve the service.

Proof Rubric — What Must Be Shown

  • SLOS: User-centered SLIs/SLOs + error-budget policy
  • TELEMETRY: Metrics, structured logs + correlated traces
  • ALERTING: Actionable pages, burn logic + runbooks
  • PROMETHEUS: Instrumented service + queryable signals
  • TOIL: Measured manual work + automation evidence
  • INCIDENT: Roles, timeline, escalation + recovery proof
  • POSTMORTEM: Blameless analysis + owned preventive actions
  • IMPROVEMENT: MTTD/MTTR + reliability/velocity learning loop
