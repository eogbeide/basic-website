Full Role Guide — What This Role Actually Does, Tools, Interview Questions & FAQ

Security Engineer roles at the level Amazon's CS Security, AppSec and SEALS teams hire for aren't primarily about running a vulnerability scanner and filing tickets. They're about secure-by-design engineering: building systems so entire classes of vulnerability are structurally hard to introduce, then verifying that with real offensive testing rather than trusting the design on paper.

The job spans a wider range than people expect coming in. Protocol and identity depth (OAuth/OIDC, IAM, least privilege) so authentication and authorization are actually correct, not just present. Application security discipline — the OWASP-style vulnerability classes, and why they keep recurring even though they're well documented. Cloud security controls, since most attack surface today is cloud infrastructure misconfiguration, not a clever zero-day. And offensive testing — threat modeling (STRIDE and similar frameworks) and penetration testing — to find what the defensive design missed.

What ties it together, and what the Advanced level of this path pushes toward, is incident response and automation: security work doesn't stop at “we fixed the bug,” it includes detecting the next attempt and responding fast enough that a caught vulnerability doesn't become a real breach. A security engineer who can only find problems, but can't help build the systems that prevent or catch them at scale, is doing half the job.

Tools of the Trade

  • Threat modeling (STRIDE or equivalent)
  • IAM/OIDC/OAuth and least-privilege access design
  • OWASP Top 10 and secure code review practice
  • Cloud security posture and configuration auditing
  • Penetration testing and offensive security basics
  • Incident response tooling and automation

Typical Interview Questions

  • Walk me through a STRIDE threat model for a simple API service.
  • How would you design least-privilege access for a multi-team cloud environment?
  • Describe a vulnerability class from the OWASP Top 10 and how you'd prevent it by design, not just patch it after the fact.
  • A security scan flags a finding your team disagrees is exploitable. How do you resolve that disagreement?
  • How do you balance shipping velocity against security review overhead without becoming the team everyone routes around?
  • Walk me through how you'd respond to an active incident where you suspect unauthorized access is ongoing.

How to Know You’re Ready

  • You can build a threat model for a real system, not just recite the STRIDE categories.
  • You've found or fixed a vulnerability using a real methodology, not just a scanner's default output.
  • You can explain why a specific vulnerability class keeps recurring despite being well documented.
  • You have an opinion on where to draw the line between blocking a risky change and enabling the team to ship it safely.

FAQ

Do I need a background in ethical hacking or CTFs to break in?

It helps demonstrate offensive skill but isn't required. Many security engineers come from software engineering backgrounds and add security depth on top — arguably an advantage, since secure-by-design work benefits from strong engineering fundamentals as much as attacker mindset.

Security Engineer vs. Penetration Tester — what's the difference?

Penetration testing is one specialized function within security engineering, focused on actively finding exploitable weaknesses. Security Engineer is usually the broader role: secure design, IAM, cloud controls, code review, and incident response, with offensive testing as one tool among several.

How do I keep up with new vulnerability classes and attack techniques?

Ongoing is the honest answer — this field has a real half-life on specific technique knowledge. What transfers is the underlying judgment: threat modeling, least-privilege thinking, and secure-by-design principles stay relevant even as specific exploits and tools change.

Role-Readiness Proof / Capstone

Secure and operate a cloud-native service end to end: build a small API/service; document data flows and a STRIDE threat model; implement OIDC/IAM and least privilege; remediate OWASP risks; configure cloud/network/data controls; add secret, dependency and CodeQL scanning in CI; run authorized Burp tests; centralize logs/detections; then investigate and contain a simulated incident. If the service uses GenAI/agents, assess prompt-injection and excessive-agent-authority risk.

Proof Rubric

Show evidence, not claims: architecture/threat model; IAM policy and auth flows; secure-code findings and fixes; cloud controls; pen-test report; CI security gates; detections/log queries; incident timeline, containment and lessons learned; quantify residual risk and explain security/usability/delivery tradeoffs.
